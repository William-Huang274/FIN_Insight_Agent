## 验收切片

1. **公共知识库与向量执行回放。**使用当前 `ResearchLibrary.navigate` 真实执行四个历史查询；按返回的文档/节点读取正文，校验候选摘要。原库和索引保持只读，提供方缓存只读，未命中即停止。不能据此声称组织权限已经覆盖公共向量库。
2. **历史报告进入组织资料链路。**通过真实 BFF/Spring/PostgreSQL 发布独立副本、关联项目并冻结所选资料；由 Python 组织来源工具实际搜索/读取，验证同项目另一资料不能进入固定输入。重启自有 Java 后恢复来源，撤权后既有引用及新搜索均拒绝。不启动研究，不使用向量或模型。
3. **授权范围内的混合检索。**已增加显式服务器配置的组织已准备向量通道，见[组织授权混合检索](organization_hybrid_retrieval.zh-CN.md)。固定资料先过滤，再进行向量/BM25/RRF 排序；缓存命中仍核权与回读原件。无配置时保留词法检索，不继承宿主混合检索开关。当前仅已有查询向量可用，任意新查询、实时 embedding/rerank 和公共库来源授权仍待后续设计。
4. **结构化查询与资料版本。**已增加[结构化 SQL 与数据卡验收](structured_sql_acceptance.zh-CN.md)：历史 SQL/数据卡身份与原文回读，宿主准备的固定数据卡快照进入 Java 组织授权；工程修订不改变旧研究输入，并验证重复导入、版本冲突、SQL 异常回滚和 Java 重启。指标卡浏览器捕获和实时团队数据库未接入；小规模测试不代表生产容量。
5. **底稿、运行与交付。**固定模型回复可以驱动当前正式图/工具；底稿可在独立副本人工构造。保存、修订、checkpoint、队列、重启及导出走真实组件，模型自主规划和金融结论质量另评。

每片同时记录业务表现、存储状态、版本/身份、失败原因和复现入口。只有实际经过的层才能标记通过。真实 SSO、金融研究质量、生产容量以及未走到的 Java→向量路径均不得从组件回放推断。

## 无付费调用的回放入口

```bash
python -m scripts.data_retrieval.replay_cached_library_scenarios \
  --library <published-library.sqlite> --index <published-vector-directory> \
  --cases <historical-query-cases.json> --as-of 2026-09-23 --output <new-output-directory>
```

该工具使用只读 SQLite 连接读取 `records-v1.sqlite`，不触发历史缓存迁移、过期删除或回写；未找到成功缓存即失败。网络连接与 embedding/rerank 提供方方法均被禁止。真实向量与原文不替换；最多读取每题前三条候选。预期来源/父节点 ID 来自历史开发题，非独立人工金标。文本改写后不得继续使用旧向量。

组织案例入口为 `tests/integration/test_historical_organization_library.py`。设置 `FIN_HISTORICAL_CASE_MANIFEST` 指向仓库外清单，并按[真实服务交付说明](organization_business_delivery.zh-CN.md)配置独立容器、jar、输出目录和已检查子网。清单包含 `question`、`as_of` 和 `documents`，每份文档列出相对 `file`、`sha256`、`query`、`expected_text` 及来源分类。文件必须位于清单所在目录内，全部摘要核对后才启动服务。

原件、副本、失败尝试和运行证据分别保留。生产资料不自动升级格式、不原地修改、不重建全量向量。测试只停止自己的服务。

## 2026-10-20 首批证据

- 历史盘点为 10 份有摘要的原始文件，包含早期半导体研究、Dell 双版本及审阅意见、Anker 准备清单、检索开发题与 case242 状态。盘点文件复核未变化；仅选取 Dell 报告创建独立输入副本。
- 公共知识库回放通过 4 个历史查询、12 次原文回读；使用实际发布库、114,900 个检索块和既有向量矩阵。8 次提供方缓存命中，0 次提供方调用。候选与回读正文摘要一致，并额外核对文档范围、父节点和长文尾部文本。运行约 244 秒，含加载与本机竞争，不能当作生产延迟或召回率指标。
- Dell 组织资料场景在真实 BFF、Spring Boot、PostgreSQL 上通过，用时约 113 秒。两份资料均关联项目，只选第一份进入冻结输入；检索只返回被选资料。重启自有 Java 后恢复同一引用；另一资料的读取以及撤权后的旧引用、新搜索均被拒绝。未启动原生 Agent，也未使用组织向量检索。
- 失败尝试分别保留：公共回放最初错误假定所有搜索结果均附带 `readback`；按现有文档/节点 ID 构造协议请求后复验。组织场景先遇不必要的原生服务健康依赖、保留网络冲突、测试读取错误标题层级；移除未使用的服务依赖、使用新独立子网、按 `current.title` 取值后通过。没有修改生产权限规则来使测试通过。

基线整合回归也暴露了一个运行问题：修订增加保存和最终提交操作后，可用动作超过旧反馈模型的 8 项上限，原本可恢复的拒绝会变成校验异常。去掉运行时内部动作列表的过时数量限制，保留非空要求；用实际组织专家图先拒绝旧式整篇提交、再保存并提交修订来验证恢复路径。其他适配涉及按工具调用身份查找回执，以及将旧测试脚本升级为当前原生工具批次协议，不改变生产提交协议。

旧底稿兼容另有一处修复：历史序列化可能省略可选的 `task_note`，原字段修改协议无法补充审阅回复。现在显式 `set_field` 可以初始化模型已声明且会持久化的可选顶层字段；不对旧底稿补默认值，不改变旧摘要，不自动补嵌套路径，也不接收任意新字段。仅用于旧请求兼容而不持久化的顶层引用别名不能通过此途径添加。保存后仍须显式最终提交及完整校验。

整合 `00122b89` 后，14 个相关测试文件首轮为 238 通过、1 失败；失败项正是上述不持久化引用别名的边界。修正后字段修改、草稿生命周期与修订提交相关 4 个文件全部通过（45 项，含该失败项），未再次全量执行已通过的其他文件。两组数量有重叠，不相加作为独立覆盖数。活跃基线检查与仓库密钥扫描通过。
