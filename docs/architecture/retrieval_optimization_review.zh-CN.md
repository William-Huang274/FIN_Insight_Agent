# 知识库、结构化数据库与图检索优化方案

状态：待用户审阅的实施方案；本文不代表功能已实现。更新日期：2026-09-22。

延续 [原文子块与向量合同](library_chunks_and_vectors.zh-CN.md)、[指标工作区](metric_workspace.zh-CN.md)和[六维来源资格路线](../engineering/six_source_qualification.zh-CN.md)。本轮仅整理方案，不修改运行服务、不更换数据版本、不执行付费调用。原资料补充缺口继续保留。

## 1. 目标与范围

两条实施主线：

1. **图辅助混合检索与上下文构建**：根据问题找到实体、相关关系和具体证据，同时保留独立文本召回，避免图漏边导致原文无法被找到。
2. **数据库、索引和读取执行优化**：消除反复初始化、全文扫描校验、重复图展开、逐条查询和过早加载正文；结构化指标按筛选条件直接取数。

共同质量约束：来源、实体、证券身份、期间、单位、修订、可知日期与证据定位保持正确；以原文为起点检查关系遗漏。检索速度、数据处理覆盖率、事实正确率分别验收。

本期复用已有子块及 Qwen3.7 正文向量。暂不默认迁移图数据库、训练图模型、全库重切或重新向量化，也不把社区报告和多轮 DRIFT 设为所有问题的必经路径。后续新增关系描述向量可独立增量构建，另记实际调用范围。

## 2. 当前依据与尚未证明的部分

当前发布基线包含 114,900 个子块，由 114,610 条唯一正文向量覆盖。静态边的 983 条引文绑定与 751 条父片段绑定只说明已有边的定位情况，不能作为从原文提取关系的召回率。

最近一次缓存诊断完成一个正式搜索及三次读取，第二个搜索主动中止，不计完整结果：

| 观察 | 耗时 | 解释边界 |
| --- | --- | --- |
| 普通全文查询的一条 SQL | 约 45.5 秒 | 需要优化执行计划与数据读取 |
| 图证据全文查询的一条 SQL | 约 37.1 秒 | 与图检索阶段计时存在嵌套 |
| 两次图展开 | 合计约 21.5 秒 | 存在重复展开和逐边读取 |
| 向量相似度计算 | 约 2.5 秒 | 当前不是第一优先瓶颈 |
| 三次来源库完整 SHA 扫描 | 每次约 115—127 秒 | 一次诊断初始化、两次正式路径构造 |

上述数值不是稳定 P50/P95，不能直接相加；缓存与正式付费执行的时间差不能全归给 API。Windows 绑定挂载已确认，原生卷对照尚未做。结构化指标查询发现先读取公司记录、再进行部分应用层筛选的代码路径，但其耗时尚未独立测量，属于待验证优化对象。

## 3. 统一的查询流程

```text
问题 + 主体/资料范围 + 研究截止日
                ↓
规范化查询：实体、指标/关系类型、期间、可知时间、版本
                ↓
  ┌─────────────┼────────────────┐
  │结构化数据查询│图关系候选与证据 │BM25 + 正文向量候选
  └─────────────┼────────────────┘
                ↓
资格过滤、候选合并、去重与初步排名
                ↓
批量读取候选正文 → 必要的模型重排
                ↓
补入入选证据所需的表头、脚注、相邻段落
                ↓
返回指标数据卡 / 关系记录 / 原文证据 / 覆盖边界
```

“候选合并”不表示结构化指标要被统一换算成文本相关性分数。精确指标查询直接返回记录和数据卡；需要解释时再补原文。精确关系列表也保留结构化排序和分页，不让重排截断冒充完整名单。

### 3.1 查询类型与通路

| 问题 | 主通路 | 辅助通路 |
| --- | --- | --- |
| 某财年毛利率、历史 PE、多公司指标比较 | 指标目录 → 参数化 SQL → 观测/数据卡 | 原文、计算操作数、口径规则 |
| 客户、供应商、融资、持仓关系 | 实体定位 → 类型/时间约束图展开 → 证据 | 独立全文与向量召回补充图外事实 |
| 经营原因、风险、管理层解释 | BM25 与正文向量混合检索 | 图提供主体和相关交易上下文 |
| 是否披露、为什么缺失 | 覆盖记录及核查范围 + 原文验证 | 执行错误与未披露分开 |
| 跨公司、跨行业综合问题 | 分解为可查的指标/关系/文本子问题 | 后续按实测考虑社区辅助路由 |

优先使用明确实体 ID、指标目录及参数；模糊输入才做语义定位。不能把一个含混的问题静默解释成另一家公司或另一期间，也不能仅按指标名字相似进行跨公司比较。

## 4. 主线 A：图辅助检索与知识库查询

### A1. 有约束的局部展开

- 统一实体及别名定位；集团、子公司、产品、证券保留不同身份。
- 按关系类型、方向、有效期间、披露可知日及审核状态选边。持仓、投资、供货、采购、合作、政策适用与共现分开。
- 同一层批量取邻接关系，使用已访问集合防止循环；确有需要再展开下一层。每层预算、排序和截断都可见，不把截断后的列表称作全部关系。
- 高连接度持仓机构和普通共现避免挤占供应链候选；使用分类型预算，具体额度在开发题集确定。
- 从关系证据映射直接获取 chunk ID。正文相关性仅用于候选内部选择与解释，避免逐边重新进行全文检索。
- 同一请求的图展开结果复用；跨请求缓存必须包含版本、主体、类型、截止日、范围和审核策略。

### A2. 混合召回、去重与重排

- BM25 从倒排索引统计打分；向量从已生成矩阵打分。先返回 ID、各通路分数及必要元数据，正文在候选合并后批量读取。
- 来源权限（适用时）、项目/文档边界、可知日等资格限制必须在正确的候选选择过程中生效。禁止先全局取很小的 Top K，再过滤到没有结果。
- 保留 BM25、稠密、图候选的来源和独立排名；可验证 RRF 等排名融合，不能直接相加不同通路的原始分数。
- 先按 chunk ID 去重，再处理同一来源重叠窗口。跨期间、不同披露版本、相反事实不能仅因语义相近合并掉。
- 模型重排读取完整候选正文与定位上下文；最终证据补齐必要表头、脚注、代词前文和交易条件。必要上下文超出预算时返回续读入口与不完整状态，不能无标记截断。
- 检查中文问英文材料、实体别名、术语及宽泛 OR 查询。词法扩展在开发集验证后启用，不能为了减少候选统一改成全 AND。

### A3. 原文到图的反向覆盖审计

已完成“边 → chunk 绑定”不代表完成“原文 → 应有关系提取”。审计按文档版本、章节/表格及原文范围记录，重叠子块不重复计处理覆盖。

记录已处理范围、解析异常、抽取版本、候选关系、正式关系、未归类候选、拒绝原因与待核项。没有实体名、关键词未命中或模型返回空，都不能单独作为已检查且无关系的证据。

在具代表性的中英文正文、财报表格、公告中独立标注应有关系，测关系精确率、召回率、主体归一、方向/期间/状态正确率及引文支持率。首轮只做固定样本审计；扩大关系补取/模型抽取作为有明确规模的后续工作包，保持原已冻结资料缺口。

检索发现图外明确事实时，可带引用返回“原文支持、尚未进入核实关系表”的候选；正式写入需经过提取校验与新版本发布。不能用模型置信分代替原文证据。

### A4. 社区与语义路由的启用条件

先实现局部图与文本联合上下文。仅当跨行业综合题表明局部方法确实漏掉有关区域，再试验重叠主题簇、实体/关系描述向量或社区报告。社区摘要作为导航，最终事实仍回到原文。保留独立全局召回，避免粗路由错误永久排除证据。

## 5. 主线 B：数据库、索引与运行性能

### B1. 数据版本验证与实例生命周期

- 对不可变发布版本进行完整来源、矩阵和映射验证；成功后按版本、规范路径、manifest 和模型配置复用验证结果及索引实例。
- 请求仍检查所选版本和必要身份，不在每次请求构造时全量扫描文件。文件替换、版本切换或身份不一致触发失效与重新验证，不能仅修改摘要绕过校验。
- 保留每请求的项目、访问范围和执行环境；复用资源不等于复用上一个用户/任务的权限或查询状态。
- 重启可以有明确的预加载与就绪检查，冷启动耗时与就绪后的查询耗时分开统计。

### B2. FTS 与图查询执行计划

- 保持当前 BM25 权重，比较 FTS5 rank 排序与现有排序方式，检查临时排序、全文表关联和实际读取行数；执行计划改善不直接当作速度结果。
- 来源与日期资格过滤后正确选择 Top K；ID 候选阶段减少正文列和 JSON 反序列化。
- 图候选集较小时，验证候选集内词法评分的执行策略；较大时验证连接/过滤计划。避免外表过滤仍触发全局宽查询，避免全局 Top K 与图集合取交集造成漏召回。
- 批量加载边、chunk 链接、覆盖状态和正文，消除逐边三次查询、逐向量命中一次查询等模式。
- 根据实际计划补实体端点、关系类型、证据映射、来源与时间索引；不预先堆叠所有索引。合理复用只读连接，遵守运行时线程边界。

### B3. 结构化数据专用查询

- 对财务、衍生指标、行情、持仓及行业观察分别测量 SQL、应用层投影、JSON 处理、排序和返回大小。
- 将可安全执行的主体、指标、期间、日期、版本及状态条件下推到 SQL，避免每次读出公司的全部记录后才筛选。业务口径规则继续参与资格判断。
- 数据卡按记录 ID 直接定位；列表默认只返回展示所需字段，公式、操作数及详细原文按卡片读取。
- 区分交易日、财务起止日、财年期间、发布/可知日和系统入库时间。历史估值只能采用该交易时点已知的财务与证券口径，不使用未来修订数据回填“当时可知”。最新修订视图与历史时点视图显式区分。
- 周/月显示保留既定采样含义：所选范围内最后一个有记录交易日，保留该日缺项，不能悄悄沿用前一有效值。采样、修订选择和口径分组后再分页，不能先截页再采样。
- 多公司批量查询；比较依指标定义、单位、实际/计划、期间与业务范围规则分组，图表抽样与精确列表分别处理。保持已发布数据卡与查询字段兼容。
- 深分页问题实测后选择稳定游标；排序增加唯一记录 ID 作为并列顺序，保证翻页不重复或漏项。

### B4. 存储与缓存

- 相同库、相同请求比较 Windows bind mount 与 Linux 原生卷；记录磁盘、内存、缓存、冷/热状态和并发，避免把预热差异当作卷性能差异。
- 空间足够且对照有收益后才迁移；保留原版本、校验及回滚入口。不因为虚拟盘已存在就认为当前库已经位于原生文件系统。
- 缓存键包含库/索引/查询策略版本、模型、过滤条件、截止日和访问范围。设置容量与失效机制，记录命中率；结果缓存不掩盖首次查询慢的问题。
- 向量部分先复用矩阵和验证结果；必要时用部分 Top K 替换完整排序。ANN 留到规模或实测需要时评估，现阶段不以重建向量解决 SQL 慢的问题。

## 6. 统一工具与 Java 迁移边界

前端和研究 Agent 使用同一查询服务及同一发布版本，职责包括：实体定位、指标目录与查询、关系查询、原文搜索、批量证据读取、指标卡、覆盖说明。接口名称可复用既有工具，新增字段保持向后兼容。

请求明确实体/证券、文档/项目范围、关系或指标类型、期间/日期及研究截止日。响应保留稳定 ID、数据版本、来源与证据、金融口径、执行状态、截断及分页、缺口原因；各通路评分属于检索解释，不是事实可信度。

执行错误、合法空结果、尚未处理、范围内未发现披露、匿名披露分别表达。禁止用空列表吞掉超时、版本错误或索引不完整。

数据库与搜索索引由薄适配层接入；对外通过稳定 JSON/HTTP 合同，模型客户端与可选 GraphRAG 组件置于适配层之后。Java 通过稳定合同调用 Python 研究资料服务，Python 可以长期承担该职责；后续只有明确工程需求与验证结果支持时，才替换具体能力实现，避免业务端依赖框架内部对象。

2026-09-23 已与 Java 接入方案任务完成[初步接口对齐](java_research_service_contract.zh-CN.md)：冻结七类逻辑能力及授权、快照、证据/数值语义、付费幂等和 SSE 续读边界。现有局部能力不等于新跨服务合同已实现；详细 OpenAPI 与接入验收仍待实施。

Neo4j 是可供多语言使用的独立数据库，Microsoft GraphRAG 现成实现主要为 Python。当前选择采用 GraphRAG 的检索组织方式，不等于决定引入全套 Microsoft 流水线或迁移 Neo4j。成熟组件先小范围适配同一合同，再依据质量、成本与运维决定替换范围。

## 7. 实施顺序与交付

| 阶段 | 工作与交付 | 完成判断 |
| --- | --- | --- |
| 0 固定基线 | 固定发布版本、40 题、参考证据、阶段计时及错误类别 | 至少 8 题作未用于调参的迁移验收；已知缺口单列 |
| 1 查询执行 | 版本验证复用、FTS 计划、批量取数、图结果复用 | 同一问题资格边界正确，执行错误可见，冷/热耗时可复现 |
| 2 结构化查询 | 指标筛选下推、直接卡片、多公司批量、采样和分页 | 值、期间、单位、修订、可知日与原实现/原文逐项核对 |
| 3 图与文本联合上下文 | 类型约束局部展开、候选融合、批量读文、证据补全 | 独立文本通路保留，多证据题完整性与图外事实可检索 |
| 4 关系覆盖审计 | 固定原文样本反查漏边、分类缺口、抽取组件对照 | 有样本精确率/召回率及逐项错误清单；不以边数代替覆盖 |
| 5 联合验收发布 | 相同版本前端/正式工具回读、路线消融、有限模型使用验证 | 速度、取证质量和模型消费分别报告；可回滚 |

阶段 0 中准备关系标注，阶段 4 才扩大专项审计与决定后续补录范围。存储对照可在阶段 1 中独立执行，是否迁卷以结果为准。发现会影响基准证据的已有解析/映射错误时先修并冻结新基线，不能边补数据边宣称算法提升。

## 8. 验收指标与建议目标

沿用 40 题计划：20 题基础定位/结构化取数、8 题关系与组合证据、6 题期间/修订/口径、6 题合理缺口。至少 8 题使用未参与调参的不同材料。既有 12 题/271 候选和 4 次正式诊断只作开发参考，不能作为新的独立测试。

| 维度 | 记录内容与门槛 |
| --- | --- |
| 结构化取数 | 可回答题的记录、值、单位、期间、状态、来源逐字段正确；基准明确错误必须修复 |
| 文本取证 | Recall@10、MRR、多证据集合完整命中率；报告分母和可替代证据，不以同公司文档命中替代答案证据 |
| 图覆盖 | 已标注原文中的关系召回/精确率，实体归一、方向、期间、状态正确率，证据支持率 |
| 漏图与错误边界 | 图无边但原文有事实仍可检索；图候选/匿名信息不升级为具名事实；执行错误不变成未披露 |
| 版本与历史 | 前端/正式工具同版；跨项目隔离（适用时）、旧引用兼容、截止日及修订无穿越 |
| 性能 | 冷启动、就绪后首次查询、暖查询分别测；总耗时及 SQL/图/向量/正文/API 分段，查询次数、候选量、内存 |

建议工程目标（供审阅，尚未实测承诺）：在本地单并发、服务就绪且不依赖结果缓存时，直接数据卡/常规指标查询 P95 ≤ 1 秒；不含外部 API 的混合候选与证据组装 P95 ≤ 5 秒。现场基线与资源测量后确认可行性；重查询、并发和冷启动另报。包含 embedding/rerank 的端到端延迟单独量化，不能把供应商耗时藏到指标之外或重复付费凑样本。

缓存/离线性能回放建议至少 100 次，按问题类别均衡，报告样本数与测试状态；已有模型响应只能在完全相同输入/模型合同下复用。候选变化后没有有效重排缓存时，先测不含付费重排的候选质量，不能伪装为完整重排结果。

速度优化不得引入已知关键证据回归；出现召回损失必须报告并修复/回退。小样本 40 题不宣称总体生产正确率或稳定统计显著性。上线前按 BM25、+向量、+图、+重排做有界消融，确认收益来自哪一层。

## 9. 成本、发布与回滚

- 初期代码/SQL优化与本地缓存回放不需要重新生成正文向量。
- 新的抽取、实体/社区描述向量、查询向量、重排或 DS 使用评测属于独立付费范围：执行前列明目的、输入规模、所需输出、质量风险、推理配置、上限和停止条件。
- 成功缓存按精确输入复用；失败和用量未知回执保留，未经针对性授权不自动重发。
- 冻结主库与索引；新索引、物化表或关系补录先构建候选版本再校验发布。若只改查询代码，保留原数据身份。
- 前端和正式工具同版切换，校验旧链接与数据卡后再推广；保留旧代码/版本配置回退。全文索引更改与资料更新分开归因。
