# 组织研究并发、检索质量与版本发布验收

本计划承接固定历史案例的业务闭环，交付可复现的工程指标。用户要求涵盖多人发起研究、网页与 Agent 的真实存储访问性能、新题召回评测、索引版本绑定和新查询向量。不得用静态测试数量代替吞吐、延迟或检索质量，也不得将本机指标写成生产规模。

## 测量合同

- 多人研究使用不同验收身份，不能把同一账号的多个线程称作多人。同一请求的重复提交、正常独立提交分开计数。测量准备、首次受理、排队、完成分别耗时；只有实际获得成功响应且后验身份/结果正确才记成功。
- 模型决策可使用明确标记的脚本；BFF、Spring、PostgreSQL、Redis、Agent Server、授权、工具、checkpoint 为真实组件。该吞吐是业务与执行框架能力，不是云模型生成吞吐。新查询 embedding 使用明确批准的来源，独立报告其成本与延迟。2026-10-20 用户明确授权付费向量生成；沿用百炼适配器，生成式研究模型仍不付费调用。
- 并发从 1、4、8 逐级增加，根据资源余量再决定 16。每级先校验正确性再延长采样，记录闭环并发模型和请求总量；不得将短批次的峰值外推成持续容量。超时、错误和排队均进入原始样本；延迟同时报告成功样本及全体终结请求，不隐藏失败。
- 网页测页面实际接口、渲染耗时；Agent 测真实工具入口。公共库、组织资料与 SQL 分组，冷启动、首次查询、重复查询分组，不能混合成一个容易误解的 P95。
- 使用独立 worktree、数据库/卷、随机端口和已检查子网；不重启共享 Docker，不改变隔壁运行。逐级压测受内存、CPU、磁盘和服务健康停止线约束；到达停止线保存失败，不能提高负载硬跑。
- 所有输出在仓库外，保存版本、构建/语料/模型/题集摘要、机器与进程配置、原始样本及汇总计算方式。最终回归使用同一版本。

## 检索质量合同

题集覆盖精确财务事实、期间/单位区分、中文问英文资料、同义表达、跨来源证据、公司消歧、历史修订和无答案/越权问题。目标首版至少 100 题；实际交付题数与每层标签质量必须据实报告。先从来源标记可核查证据，再写自然语言问题；不能从已返回的候选反向选择“正确答案”。

开发集与保留集按来源/问题家族分离，冻结后保存摘要。标注至少包含来源、版本、节点或证据跨度、相关等级与理由。完整来源标签尚未穷尽时称为“已标注证据召回率”，不能冒充全库所有相关材料召回率。多证据题单独报告全证据覆盖率；无答案题单独报告错误给证据比例。权限隔离正确率与内容相关性分别评价。

同题对照关键词、向量、混合检索；模型、语料、切块、过滤、K 与重排配置均记录。本地量化模型与历史云端向量不混用，不将两种模型下的变化全归因于代码优化。正式保留集结果不得成为反复调参训练集。

## 新查询与索引版本合同

组织 release 由可信服务器发布并登记模型身份、维度、文本投影版本、矩阵和节点摘要。Java 准备单只能引用同组织的已登记 release，原 manifest 字节和旧摘要不改写。Python 运行时按准备单身份读取固定 release，不能默默追随宿主“最新目录”。

新查询的模型来源由服务器配置，工具参数不能指定网络地址或模型文件。仅在模型身份与索引一致时生成查询向量，成功后保存按模型/索引/查询划分的缓存。超时、限流、不可用、错误维度或非有限数字是执行失败，不能变成“资料不存在”或静默词法回退；失败不得写为成功缓存，不自动重试未知请求。

## 向量生成预算

Purpose：验证新查询来源及新题语义检索，付费范围限定 embedding。Input scale：先小批公开文本验证回执与缓存，再按语料、题集及已存在的同模型向量计算缺口；不直接重嵌全库。Output：每段固定维度向量与模型/输入摘要，不生成研究答案。Quality risk：模型混用、截断或错误输入投影导致语义失真。Reasoning profile：embedding，不适用推理生成。Limits：每个执行批次先保存机器可读 TokenBudgetBasis；初始探针最多 10 条、10,000 UTF-8 字节、一次服务请求，SDK 重试为零。扩展批次另存实际输入规模与预算，保持低并发，避免争用同账户额度。Stop：超预算、限流、未知结果、模型/维度/健康不符即停止该批；保留失败及未知用量，不自动补发。成功缓存仅在来源范围、模型、维度、完整文本及输入投影一致时复用。

2026-10-20 查询的百炼中国内地 `text-embedding-v4` 官方报价为每百万输入 token 0.5 元（[官方模型页](https://help.aliyun.com/zh/model-studio/text-embedding-v4)）。报价用于估算，账本保存服务实际 token 回执；免费额度、账户优惠及最终账单不据此推断。新索引与查询须使用相同模型和维度，不能因为同为 1,024 维就跨模型复用。

## 首轮诊断（2026-10-20）

实际已有完整索引是 `qwen3.7-text-embedding`、1,024 维，覆盖 114,900 个子块和 114,610 个独立向量。因此本次向量探针也选用 3.7，而非按 v4 的报价选择模型。只发出 1 次真实 embedding 请求，回执记录 39 个输入/总 token，得到有效向量；恢复持久缓存后调用次数为零。单次含客户端初始化的耗时约 2.38 秒，仅作连通性记录。用量原始回执和本次新增用量分开返回，缓存命中不能重复计费。这里尚未把新查询来源接入 Java 的冻结索引合同。

多人诊断以 8 个独立验收身份、2 个组织项目、同一真实 NVIDIA 历史披露片段执行。每次经过真实 BFF、Spring、PostgreSQL、Redis、Agent Server、资料权限核验及原文回读，并核对草稿 `created_by`、唯一 thread/run、三次静态模型决策和完成 checkpoint。OIDC 身份和模型决策为明确的验收替身；没有付费生成模型。

总验收约 275 秒，包括启动、建库、成员准备与清理。机器同时运行其他任务；本次自有原生服务限制 1.5 CPU、1.5 GiB、`N_JOBS_PER_WORKER=1`，Java 堆上限 256 MiB。压测采用闭环请求，原始样本保留各阶段延迟及失败，不是开放到达率测试。受理后至完成包含排队与执行，尚未拆成纯队列延迟；上述增长不能单凭此表归因为 Java 或数据库瓶颈。

每档只有 8 个样本，P95/P99 在该样本量下等于最大值，因此正文只报告最大值。**这不是持续容量结论，也不是最终简历指标。** 没有改动共享服务配置或已有数据库；只停止本轮独立进程和容器，原始输出与数据库保留在仓库外。下一轮须补足持续采样、运行队列观测和资源干扰记录，再结合检索延迟及新题召回结果形成最终指标。
