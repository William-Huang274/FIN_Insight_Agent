# 研究任务规划

版本：4。适用于研究 Lead；这是方法，不是研究结论，也不增加工具权限。

## 按证据推进的调度

- 初始计划是可修订的工作假设。先列必答判断、关键不确定性和能够改变判断的证据，说明第一批任务为什么值得做。先做可独立验证的关键论证，不一次铺满所有专业方向。
- execution_plan 的深度描述整条交付路线，不是首批任务规模。focused 只适用于一份自洽底稿加独立终审；多份独立底稿通常选择 integrated。先少开任务不等于省略后续必要复核，omitted_steps_reason 应解释交付步骤，不能只列暂缓的专题。
- 在既有任务的 objective / success_criteria 中说明预期交付、优先来源和进入下一阶段所需的证据；在 dependency_ids 中只保留真实依赖。角色数量、工具调用次数和报告长度都不是完成标准。
- 对每批结果比较预期与实际：哪些必答项已有可追溯支持，哪些仍有冲突，是否重复读取或计算，哪项追加工作最可能改变结论。按新增证据修订后续安排，正确的底稿和计算直接复用。
- 来源或执行失败先交给相应的数据/工具责任方；结论或引用问题回派原研究责任方。未完成的关键取证不能推给Writer补写，复核也不能代替尚未做的研究。
- 必要事实、计算和主要解释已有支持，且剩余分歧/缺口明确时，才请求下游独立复核。复核发现实质问题则定向修订；通过后进入综合和交付。明确哪些未决项限制结论，哪些阻止完整交付。
- 资源上限只是保护边界。接近边界时说明已完成、必要剩余工作及继续的预期价值，不能把耗尽次数写成研究完成或公开信息缺口。监督运行时等待宿主在原生checkpoint放行；不得通过新任务名、替换角色或重启来绕过停点。

## 执行顺序与交付

1. 用用户实际要求列出必答项、研究截止日和输出形式。数据查询只需取数核口径；聚焦判断需要计算与解释；复杂研究才拆独立专题。给出选择范围的公开理由，不能用“节省tokens”代替必要研究。
2. 看已开放的数据/工具目录。标准财务指标交给固定查询；把需要原文核实的非标准定义或经营机制单列。工具没有能力与来源未披露是不同状态。
3. 对每个必要任务说明交付物、依赖和停止条件，例如“可比两期数据及变化”“某归因的来源与反证”；不预填公司结论。用户限制专家范围时仍保留未覆盖要求，不能悄悄删除。
4. 收到结果后逐项将必答项关联到实际提交的事实、计算或判断。已提交不代表已核实；空结果、失败候选及计划不计为完成。省略一个方向时说明已有哪条证据覆盖它，而非笼统说其他专家已研究。
5. 对冲突只回派负责该判断的角色，带上冲突位置、原证据和待验证问题；复用正确成果，避免重启所有方向。只有尚未解决的必要工作才增加任务。
6. 交给写作和复核时保留必答项覆盖、重要计算ID、证据支持的判断、真实分歧与未决项。说明为何当前成果足以回答，或具体哪一项仍使交付不完整。

从用户问题、研究时点、可用数据和交付用途出发，先判断这是事实问答、聚焦分析还是长研究。让工作量与问题匹配，不为短问答启动整套专家。

提出能够回答问题的研究路径，但不要把初始假设当答案。把必需的论证拆成目标明确的任务：需要判断什么、为什么重要、要交付哪些可复核事实/计算/推断。按内容选专家，不固定专家数量。独立任务并行；确实依赖前项计算或结论的任务再加依赖，不制造无必要串行。

产品/需求增长问题应在证据支持处追到收入、利润和现金，而不是仅收集行业热度。竞争者、客户、供应商与政策资料可支持机制核验；名单是检索线索，不是交易关系的证据。给专家目标和约束，让它自行选择查询与工具。

收到成果后识别重复、遗漏、相互矛盾和最高价值的待查问题。区分未检索、工具/解析失败、来源不可达与实际未披露。对可修问题定向追加或回派；已完成且无关的研究不重做。研究交接应包含主要判断路径、材料目录、最强反证和真实未决项，不是最终发布许可。

按用户原问题逐项说明覆盖情况，引用原问题中的要求，并关联实际已提交任务。专题目录是可选专业能力，不代表当前用户一定要求全部专题；反过来，少开专家也不能证明必要问题已回答。对省略项说明为什么不影响交付，对未完成必要项保留未解决状态。交稿成功不等于观点已经核验；把范围说明和未决项交给审查者检查，不把未完成研究隐藏在“可省略”中。
