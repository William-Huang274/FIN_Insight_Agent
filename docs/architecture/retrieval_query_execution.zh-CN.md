# 检索与数据库查询执行优化

2026-09-23，实施中。遵循[已批准方案](retrieval_optimization_review.zh-CN.md)及[Java 服务边界](java_research_service_contract.zh-CN.md)。本文区分已实现的执行优化与尚待完成的研究质量验收。

## 已实现的首批改动

- 不可变库校验按规范路径、文件身份及预期 SHA 复用。文件改变触发重新校验；并发冷启动串行校验，避免重复扫描。每个实例仍保留自己的请求环境。缓存不是访问授权。
- FTS5 使用既有 BM25 权重，在来源资格限制内选择候选 ID，再批量读取正文。没有先截全局 Top K 再过滤来源。图候选保留同分 ID 排序。
- 图证据和覆盖状态按批查询，保留每边八条子块窗口、父片段、绑定状态和动态关系回读边界。单请求深度一图结果复用；深度二保留原独立展开语义。
- 稠密与图候选先以 ID 合并，按原配额和顺序批量读文。记录各通路候选名次和重排分数；这些是检索解释，不是事实置信度。
- 指标卡直接按记录 ID、主体及可知日查询；不再预读全公司历史。财年锚点按实际期间去重。计算指标卡也应用现有口径核查说明，修复列表有说明而卡片遗漏的情况。

未改 chunk、来源身份、已有向量及公式数值；没有付费调用或全库重建。公开资料查询仍不等于 Java 跨服务授权/快照合同已经实现。

## 当前验证及限制

首批工程回归 63 项通过，覆盖时间/文档资格、模型身份、图绑定、卡片与旧请求兼容。真实库六家公司图结果与原实现一致；核心二十家历史查询结果一致。部分计算卡片增加之前遗漏的核查说明，数值等事实字段须单独核对，不把这些差异藏在“完全相同”声明中。

同一 r21 库、单并发、Docker Windows 绑定挂载中的四个开发查询：原全文 SQL 22.6–61.4 秒，修改后 1.1–1.7 秒，Top 40 顺序一致。一次完整初始化约 67.8 秒，同进程再次构造约 0.068 秒。这是一次顺序对照，包含缓存/预热影响；不是整体混合检索 P95，也不是模型答案正确率。

可复用无模型性能回放：

```bash
python -m scripts.data_retrieval.benchmark_library_queries --library <immutable.sqlite> --cases <local-cases.json> --output <local-results.json> --repeats 3
```

cases 包含 `library_sha256` 和具有唯一 `id` 的 `cases`；各项包括 `operation`（search/graph/metric/read）、相应函数 `arguments` 及可选 `expected_sha256`。回放校验固定库身份，保存每次耗时、结果摘要及分通路分位数；不调用 embedding、重排或回答模型。错误直接失败，不能转换成合法空值。生成的题集和运行结果留在本地，不能将由原实现生成的结果摘要称为独立人工参考答案。

完整四十题答案/依据评审、关系遗漏的原文独立标注、更多查询筛选下推、图类型路由和上下文质量、正式工具联合发布验收仍按方案继续。本轮执行回归只证明保持现有输出，不能证明现有资料没有漏边或所有财务事实正确。
